# 自動排班離線工具

用網站同一份排班核心（`auto-schedule-core.js`、`shift-utils.js`、`holidays.js`）在電腦上跑，
改規則或調權重之前，先用這些工具確認「待補有沒有變多、人事成本有沒有增加」。

**只讀資料庫，不會寫入任何東西。**

## 第一次使用

```bash
gcloud auth application-default login   # 用 Google 帳號登入（有 store-schedule-3b056 權限的那個）
cd functions && npm install && cd ..    # 工具借用 functions 裡的 firebase-admin
```

⚠️ **這個 repo 是公開的**：
- 程式碼裡不放任何金鑰，讀資料庫用上面那個預設登入。
- 抓下來的資料（姓名、班表、薪資）存在 `tools/autosched/.cache/`，已經列入 `.gitignore`，**不可提交**。

## 三支工具

### 連續試排 `simulate.js`
從某週排到某週，每週的草稿當成已排好再排下一週（跟店長每週按「產生草稿」一樣）。
列出每週的待補、整段統計，以及涵蓋月份的人事成本。

```bash
node tools/autosched/simulate.js --store 美德 --from 2026-W41 --to 2026-W49
```

| 選項 | 說明 |
|---|---|
| `--cache` | 用上次抓的資料，不重抓（快很多） |
| `--weights '{"gapDay":12000}'` | 覆寫權重（權重名稱見 `auto-schedule-core.js` 的 `W`） |
| `--salary 2026-09` | 正職底薪取哪個月的薪資記錄（預設本月或上月最近一個有記錄的） |
| `--quiet` | 只印統計 |

### 回測 `backtest.js`
拿已經過去的週，把「自動排班的人」的格子清空，只留手動排的人與劃休，讓草稿重排，
再跟店長實際排的比較（缺人、待補、正職加班、工讀時數、11 小時間隔、連上天數）。

```bash
node tools/autosched/backtest.js --store 美德 --from 2026-W26 --to 2026-W38 --cache
```

| 選項 | 說明 |
|---|---|
| `--season` | 打開寒暑假分季（網站目前關閉；回測 7、8 月時打開才公平） |
| `--infer` | 不用存好的設定，改用歷史推算（評估還沒設定的門市用；結果偏樂觀） |
| `--weights` / `--cache` | 同上 |

⚠️ 設定是「現在」的（可上班別、每人上限），越早的週結果越只能參考。

### 調參 `tune.js`
用不同權重跑同一段連續試排，一行一組比較。

```bash
node tools/autosched/tune.js --store 美德 --from 2026-W41 --to 2026-W49 --cache \
  --sets '[["目前",{}],["gapDay 0",{"gapDay":0}],["gapDay 20000",{"gapDay":20000}]]'
```

變動成本＝工讀時數×時薪×1.06＋國定假日加給＋正職加班費＋待補時數×196×1.06（假設用工讀補）。
正職底薪固定，不影響比較，所以不算在內。

⚠️ 草稿有隨機起點，權重差一點的組別結果會有起伏：**看趨勢，不要看單一數字**。

## 成本口徑（`simulate.js` 的月成本表）

- 正職＝底薪＋全勤＋公司勞退，**以當月薪資記錄判斷誰是正職**（有人月中轉工讀，用現況身分會重複計算）；沒有當月記錄就用 `--salary` 那個月的
- 工讀＝時數×時薪×1.06（含勞退）；國定假日加給＝時數×時薪
- 正職加班＝（一天超過 8 小時＋每週正常工時超過 40 小時）×底薪÷240×1.34
- 待補＝時數×196×1.06（假設用工讀補；實際靠跨店支援的話錢算在別店）
- 都不含勞健保公司負擔
